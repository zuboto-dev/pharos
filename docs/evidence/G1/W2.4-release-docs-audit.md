## Findings for W2.5

### F01 — Missing README troubleshooting section (completeness)

Location: `README.md:26` through `README.md:173`; no troubleshooting heading exists. There is no missing text to quote. The closest recovery advice is “Stop the service before `pnpm dev`, since both listen on port 4300” (`README.md:61–62`).

Current behavior: `apps/server/src/index.ts:79–85` detects `EADDRINUSE` and suggests stopping the other server or using another port. `apps/web/vite.config.ts:5–11` independently chooses the dev proxy destination from `PHAROS_SERVER_URL`. `agent-runner.ts:47–58` distinguishes off/unavailable/custom/default modes; `:147–168` distinguishes resume from explicitly answering waiting questions. The required troubleshooting section should cover these existing recovery paths, MCP connection/database mismatches, and where to inspect configured logs. A scattered port warning does not satisfy the requested section.

### F02 — Stdio database sharing is conditional (accuracy)

Quote: “The stdio process uses the same database as the web server” — `README.md:105`.

Current behavior: `apps/server/src/stdio.ts:8` independently calls `openDatabase()`. `apps/server/src/store/database.ts:6–8` resolves the path from that process's `PHAROS_DB`, otherwise its home-directory default; HTTP does the same at `index.ts:25–26`. The README's stdio example at lines 94–103 has no `env` configuration. A server started with an overridden database and a separately launched MCP client with no matching override use different databases. Sharing requires both processes to resolve the same database path, including the working directory if a relative override is used. This qualification is especially relevant to the separate development database recommended by `CONTRIBUTING.md:15–19`.

### F03 — Cross-process updates are not guaranteed within one second (accuracy)

Quote: “the web app picks up its changes within a second.” — `README.md:105–106`.

Current behavior: `apps/server/src/feed.ts:15–18` defaults to a 1,000 ms poll interval, starts polling while subscribed at `:23–28`, and catches database read failures for retry on a later poll at `:43–50`. SSE delivery and the browser's subsequent fetch/render add time (`apps/server/src/app.ts:94`; `apps/web/src/lib/events.ts:33`). The implementation provides polling approximately once per second, not an end-to-end one-second guarantee. Wording should describe the polling interval and normal live-update behavior.

### F04 — Web-link default differs between dev/stdio and built HTTP serving (accuracy)

Quote: configuration row “`PHAROS_WEB_URL` | `http://localhost:5173` | Web app address used in links agents share” — `README.md:138`.

Current behavior: `apps/server/src/views/service.ts:32–34` falls back to port 5173, but `apps/server/src/index.ts:31–37` first sets an unset `PHAROS_WEB_URL` to the HTTP server's own URL whenever the built web app is served. The normal built-server default is therefore port 4300, or the configured `PORT`. The service paragraph at `README.md:60–61` already describes this exception correctly; the table does not. A separate stdio process does not execute `index.ts`, so it retains the 5173 fallback unless explicitly configured, even when sharing a database with the service.

### F05 — Service does not persist arbitrary installation environment (accuracy)

Quote: “Configuration variables set while installing are stored in the service” — `README.md:59–60`.

Current behavior: `scripts/pharos-service.sh:48–56` constructs `PATH`, stores `HOME` and `PORT`, and copies only `PHAROS_DB`, `PHAROS_AGENT_COMMAND`, `PHAROS_AGENT_LOG`, and `PHAROS_WEB_URL` from the installation environment. It does not copy arbitrary variables needed by a custom command, or the README table's `PHAROS_SERVER_URL` (which is a dev-proxy setting and not needed by the built server). `PHAROS_SERVER_LOG` is separately consumed to write launchd's output paths at `:20` and `:83–86`. The statement needs the supported list and should not imply a custom command's complete environment is captured.

### F06 — Seven days is the default answer expiry, not the only supported expiry (accuracy)

Quote: “`view_answer` creates an answer view that expires after seven days unless kept.” — `CONTRIBUTING.md:71–72`.

Current behavior: `apps/server/src/views/service.ts:23` defines a seven-day default, but `:139` accepts optional `expiresInDays` from 1 through 90, and `:165–166` uses it when supplied. Keeping clears expiry at `:220–225`. Expiration hides the view from normal listings (`:59–64`); it does not delete the stored entity. Qualify seven days as the default.

### Wording reviewed without an additional finding

`README.md:67` says the server must be running and gives `pnpm dev` parenthetically. Read with the immediately preceding service instructions, this is an example startup command, not an exclusive requirement to use dev mode. Default ports and log paths are also read as defaults in context: `PHAROS_AGENT_LOG` is explicitly documented at line 141, and service-log override behavior is captured under F05. The POSIX/WSL recommendation at lines 43–45 agrees with the `sh` probe and default shell command; `shellRunner` itself uses the platform shell via `shell: true`. These were reviewed rather than silently treated as independently proven third-party/platform guarantees.
