## 1 Purpose & goal link

**Purpose.** The owner asks what is risky or blocked and gets a focused answer view. The view states
the answer first, then shows exactly the at-risk work and why each item is at risk: blocked, overdue,
or waiting on unfinished work. It contains nothing that dilutes that answer. This is the
question → view part of the roadmap's question → view → action → refinement → reuse workflow
(`docs/PLAN.md:14`). Case B (W1.3) covers refinement and retention, and case C (W1.4) covers action
and reuse.

**Goal link.** Goal `goal_4d3e0fbc65df`, "Project questions produce reliable, useful generated
views". Stage G1, work item W1 "Define core workflows and measurable acceptance criteria", task W1.2.

**What the case exercises** (W1.1 section A): Ask dialog / widget Ask / item Ask → `request`
entity → the answering agent (runner brief `answerBrief`, `apps/server/src/guidance.ts:256`, or an
interactive MCP agent) → `view_answer` → answer view (`kind: "answer"`, `question`, `expiresAt`)
→ page announcement → Open.

## 4 Expected facts & checks

**Conventions.** A check is `{id, query, expect}`. `query` is a Pharos `Query`
(`packages/schema/src/views/query.ts`: `type` plus `where`/`anyOf`/`sort`/`limit`). The checker runs
it with `runQuery(dataset, query.type, query, {today: T})` after replacing `@ref` strings with ids.
`expect` is an exact set of refs unless it says otherwise. `OPEN` stands for
`{"not": ["done", "cancelled"]}`. Option fields match by meaning (`run-query.ts:93`, `:106`), so `"blocked"`
finds `waiting` and `["done","cancelled"]` excludes `accepted`/`dropped`.

**F3, F4, F4s, and F5 are two-step checks.** No single live filter can express "depends on an
unfinished task". References are followed one hop only through `stageId`, `assigneeId`, `taskId`,

computes `U` with F3a and then substitutes U's ids. A **view** that embeds literal id lists is
copying data and goes stale (see V6). The live alternatives are a DependencyGraph or a TaskTable with
the `dependsOn` column over unfinished work.

### 4.3 View checks (against the saved answer spec)

For each widget, the checker computes the **displayed set** the same way the renderer does
(`apps/server/src/views/preview.ts` mirrors it). DataTable/DataList/Stat/CountChart use
`runQuery(query.type, query)`. TaskTable/KanbanBoard/DependencyGraph/TaskChecklist use
`runQuery("task", filter)`. TaskChecklist also hides done tasks and applies `assigneeKind`. Text
values use `count`/`percent` of their queries. _Evidence widgets_ are the widgets that list tasks.

## 5 Allowed view shape

**Board.** One Board answer view with **2–6 widgets**, rows of 12 columns, and no width below a
component's `minColumns` (`packages/schema/src/views/catalog-info.ts`). Two widgets are allowed, as
in the checked-in "What's overdue?" example. More than 6 counts as clutter for a single risk
question, even though the general guideline allows up to 8 (`guidance.ts:26`).

**Required order**

1. **Headline**, first and full width: `Text` with live `values` (preferred) or `Callout`
   (`tone: warning`/`danger`) naming the bottleneck. It states the scope it used ("across the
   project", "in Stage 2") and the counts by reason.
2. **Primary evidence**, at most one row below the headline (one optional row of `Stat`/`StatCards`
   may sit in between): a list of the at-risk tasks with reasons visible.

**Allowed components**

| Role             | Components                                                                                                                                                                                                                | Conditions                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Headline         | `Text`, `Callout`                                                                                                                                                                                                         | Exactly one headline. A Callout must not hand-type counts.    |
| Counts           | `Stat` (2–4 in one row) or `StatCards`                                                                                                                                                                                    | Queries equal F1/F2/F3-style sets in scope                    |
| Primary evidence | `TaskTable` (columns include `status`, `dueDate`, `dependsOn`), `DataTable` (title, status, dueDate, assignee/stage), `DataList` (secondary status, dueDate), `KanbanBoard` (filtered to the risk set, `hideEmpty: true`) | Displayed set ⊆ Required ∪ Allowed. At least one is required. |
| Why/order        | `DependencyGraph` filtered to open work in scope                                                                                                                                                                          | Optional; recommended for A2/A5                               |
| Context          | `ProgressRing` (current stage, A2 only), `DecisionLog`/`DataList` filtered to `@cd.dec.renderer_wait`'s topic, `ArtifactGallery` filtered `{"task.status":"blocked"}`                                                     | At most two context widgets                                   |

**Not allowed (clutter).** `ProjectHeader`, `GoalTree`, `ScopeBoard`, `StageTracker`, `Timeline`,
`MilestoneList`, `AssigneeMatrix`, `ActivityFeed`, `CountChart` (unless the question asks "where"),
`Markdown` prose that restates data, and `Tabs`/`Grid`/`Section` wrappers. The following are also
clutter:

- an unfiltered or broadly filtered task widget (all tasks, all of the stage, or done/cancelled
  tasks shown as rows)
- two widgets showing the same set the same way
- an empty widget when the answer is not empty
- anything that requires opening another tab or the chat to understand the answer

**Above the fold.** At the reference viewport (1280×800 CSS px, default zoom, answer opened from the
announcement), without scrolling, the owner sees the headline with its counts and the scope it used,
plus at least the first three rows of the primary evidence, including `@cd.t.renderer` and
`@cd.t.api`. Structural proxy for the checker: the headline is widget 0, the evidence starts in board
row 1 or 2, and no widget above the evidence sets `h` > 240.

**Noise metric** (recorded, not gated in v1.0.0): rows in evidence widgets whose entity is not in
Required ∪ Allowed, divided by all evidence rows. The expected value is 0.

## 6 Failure & fallback behavior

| Situation                                                                        | Expected behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Outcome code                                                                                   |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Ambiguous phrasing (A4)**, runner path                                         | The runner cannot ask back: "Nobody reads your chat reply; put what you have to say in a view" (`guidance.ts:280`). The agent answers the **default interpretation**: risk = blocked ∪ overdue ∪ waiting on unfinished work, across the whole project (F4). The headline states that interpretation in words, for example "Reading 'trouble' as blocked, overdue, or waiting work: …". It may add one line suggesting narrower questions (a stage, schedule only). ## 7 Completion condition

A run of `A-risks` counts as **done** when all of these hold:

1. **Automated.** V1–V7, V9, and V10 pass for the phrasing and variant. V8 records defects only.
   Outcome code `pass`, `pass-clarified`, `pass-empty`, or `pass-reused`. `pass-defect-stale` counts as
   done-with-defect and is reported separately.
2. **Human reader.** The owner opens the answer once at the reference viewport and, **without
   scrolling, opening other tabs or drawers, or reading chat**, writes down:
   (a) how many items are at risk and the scope the answer used;
   (b) which task is blocked and which are overdue;
   then, scrolling allowed:
   (c) what each waiting task waits on (F5).
   All three answers match §4 for that phrasing. The owner also answers yes or no to "Would I
   need to ask a follow-up to understand what is risky?". The run counts as done only if the answer
   is no, or if the follow-up is the narrowing suggestion the view itself offered (A4).
3. **No silent data change** (`fail-side-effect` not triggered).

The run record captures the time from submission to the answer view existing ("time to useful
content"), total latency, and cost. G1 sets their targets separately (§9 Q7). They are not part of
"done" in v1.0.0.

## 9 Open questions for the owner

1. **What counts as "risky"?** v1.0.0 scores blocked ∪ overdue ∪ waiting on unfinished work and
   treats due-soon (F7) as optional context. Should high/urgent priority without an assignee, or a
   stage past its target date with open work, also be required risk facts?
2. **Cancelled prerequisites.** Is a task that depends on a _cancelled_ task at risk (its prerequisite
   will never finish) or unblocked? The fixture avoids this case for now.
3. **Clarification on the runner path.** Is "state the interpretation in the headline" the accepted
   behavior for ambiguous questions, or should G2/G4 add a way for the runner to ask back, for
   example an answer view that is only a question?
4. **Dependency-derived risk as a live query.** Should the filter language gain a way to follow
   `dependsOn`, such as a `dependsOn.status` hop or a special value for "has unfinished
   dependencies"? That would be a G4 gap candidate. Without it, F3 can only be shown through
   DependencyGraph/TaskTable, and a live count of "waiting" tasks (V4) is impossible. A Text headline
   can count blocked and overdue tasks live but not dependency-waiting ones.
5. **Guidance example includes cancelled work.** `guidance.ts:43` ("Blocked or overdue") uses
   `status: {not: "done"}` and so returns cancelled overdue tasks (N1, A-E2). Should it be fixed in G2,
   or kept as a measured trap for the G1 baseline and fixed afterwards? This case does not change
   product code.
6. **Empty-state wording.** Filtered `TaskTable`/`DependencyGraph`/`KanbanBoard` say "No tasks yet"
   even when tasks exist but none match. Count this as a defect in empty variants (as proposed), or
   allow it?
7. **Targets and limits.** The answer time limit for `fail-no-answer`, the reference viewport
   (proposed 1280×800), and the widget budget (proposed 2–6, tighter than the guideline's 3–8) need
   the owner's sign-off before baseline runs.
8. **Shared fixture refs.** Cases B (W1.3) and C (W1.4) are written in parallel and may name the same
   W1.1 fixtures differently. This case proposes `@cd.*`/`@wr.*` refs and the task set in §2. Which
   naming wins when the fixtures are built?
9. **Static Callout text.** A Callout that names a bottleneck by hand (as the checked-in "What's
   blocking the current stage?" example does) is true when it is written but goes stale after an
   action (case C). Is it acceptable in a _kept_ answer, or should kept risk views require a live Text?
