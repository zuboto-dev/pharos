## 1 Purpose & goal link

The person opens a view an agent generated, changes one task from that view, sees every place
that shows the task agree right away, and can trust what happened (who, what, why, and how to undo
it). Later, after other people or agents have changed the project, they reopen the same view and
get current data without asking again, and they can tell which parts are live and which are
prose written at a point in time.

- **goal_c111358c4d9b — "People can refine and act through generated views with control".** This
  case covers *act* and *control*: an action from a generated view, validation, protection
  against duplicates and stale state, undo, and visible confirmation. Case B (W1.3) covers
  *refine*.
- **goal_06edae668e9a — "Pharos manages its own planning, execution and review".** The same action
  is how the owner records execution in Pharos's own plan (variant C-6). The revision it leaves
  (author, message, before/after) is what an agent later reads with `changes_since` /
  `history_list` to review progress (`apps/server/src/mcp.ts:63`, `:179`).

### The task change: recommendation

| Candidate | Where it can be done from a view today | What it exercises | Gaps it exposes |
| --- | --- | --- | --- |
| **Status → the "done" meaning (recommended)** | Round checkbox in TaskTable, TaskChecklist, Kanban cards and the drawer title (`apps/web/src/catalog/interactive.tsx:231`, `components/work.tsx:83`, `:409`, `:478`, `catalog/drawer.tsx:358`); also the drawer Status dropdown (`drawer.tsx:70`, `:169`) and Kanban drag (`work.tsx:232`) | Meaning vs. value (`valueFor`) with custom options; changes which query-bound widgets include the task (overdue lists, counts, progress), so live updates and reuse are easy to observe | No Undo toast (`interactive.tsx:219` does not pass `undoable`); the checkbox toggles from its last-rendered state (`:244`), so duplicate clicks can reopen; no stale-write precondition |
| Owner (`assigneeId`) | Drawer Assignee dropdown (`drawer.tsx:139`, `:182`); Kanban grouped by assignee, by drag (`work.tsx:205`, `:239`) | Reference validation; TaskChecklist `assigneeKind` membership; AssigneeMatrix | Assignees are workspace-wide (`packages/schema/src/entities.ts:86`, `:173`), so there is no per-project rule to test; widget membership changes in fewer widgets |
| Due date (`dueDate`) | Drawer date input only (`drawer.tsx:204`, `editable.tsx:222`); no in-widget date control | `YYYY-MM-DD` validation; overdue membership; already has an Undo toast (`editable.tsx:28`) | Saves on every input change (`editable.tsx:231`), so keyboard entry can produce several revisions; it isn't an action *from the view* surface itself |

**Recommendation: status, set to the project's first option whose meaning is `done`, from the
round checkbox in a generated view.** Reasons: it is the most common action people take from a
view and the only one available in-widget across three task components. It is the hardest
validation rule (values differ per project and must be chosen by meaning). It moves the task in or
out of the most widgets, which makes "every view agrees" observable. And it carries the three
behavior gaps (undo, duplicate toggle, stale write) that this case exists to close. Owner and due
date are kept as variants C-1 and C-2. **The owner confirms the choice in W8** (open question Q1).

## 3 Inputs/steps

**C-main: mark `T` done from `V`.**

1. Open `V` in tab 1 and the Overview in window 2. Check the starting values recorded above.
2. In `V`, press the round checkbox labelled `Mark “Write catalog migration notes” done`
   (`interactive.tsx:240`). If `V` lists tasks with `DataTable`/`DataList`, which have no checkbox,
   click the row to open the drawer and use the checkbox next to the title (`drawer.tsx:358`).
   The status dropdown is variant C-3.
3. Expected request (today's client, `interactive.tsx:216`, `pages/ProjectPage.tsx:187`):

   ```http
   POST /api/apply            (no x-pharos-author header)
   {"message": "Mark “Write catalog migration notes” as accepted",
    "operations": [{"op": "update", "type": "task", "id": "<T>", "data": {"status": "accepted"}}]}
   ```

   The value is `valueFor(P, "task.status", "done")` = `accepted`, the first option with meaning
   `done` (`packages/schema/src/options.ts:196`). The message uses that option's label in lower
   case. The literal `done` must never be sent for `P`.
4. Expected revision `R1` (`apps/server/src/store/store.ts:398`, `:455`; `apps/server/src/app.ts:28`, `:175`):

   | Field | Expected |
   | --- | --- |
   | `id` | `R1 > R0`, the next revision |
   | `author` | `{kind: "human", name: "me"}` (the REST default when no header is sent) |
   | `message` | `Mark “Write catalog migration notes” as accepted` |
   | `revertOf` | `null` |
   | `changes` | exactly one: `op: "update"`, `type: "task"`, `id: T`, `projectId: P`, `before.status: "queued"`, `after.status: "accepted"`; every other field of `before` and `after` identical |
   | Entity | `T.data.status = "accepted"`, `T.updatedRev = R1`; nothing else in `P` changes |

5. Confirm (section 4) in both windows **without reloading or refocusing**.
6. **Undo (target).** Press Undo on the toast within 8 s (`ProjectPage.tsx:263`). Expected: revision
   `R2` with `revertOf: R1`, message `Undo: Mark “Write catalog migration notes” as accepted`
   (`ProjectPage.tsx:316`), `T.status` back to `queued`, and every widget back to its step-1
   values. Then mark `T` done again (`R3`, same shape as `R1`) so the reuse steps start from done.
   *Today the checkbox shows no toast*, so this step can only be done through History → Revert
   (`apps/web/src/catalog/history.tsx`), with a message that differs.

**C-reuse: reopen `V` after a later data change.**

7. Close tab 1 (or switch to another view). As the agent, over MCP `apply`, set `U.dueDate` to
   2026-10-06 with message "Move the catalog API review earlier: dependency slipped". Expected
   revision `R4`, author `{kind: "agent", name: <agent name>}`. Then, as the owner in window 2, edit
   any field of another task (any revision `R5`).
8. Reopen `V` from its tab, or with its URL `/projects/P/views/V` (`apps/web/src/pages/ViewTabs.tsx:167`).
   Do **not** ask the question again. Check section 4's reuse rows.

| Part of `V` | Kind | Expected on reopen |
| --- | --- | --- |

What the person should see: current data in every bound widget, with no new question and no
agent run, and prose that is plainly the agent's earlier note. **Today** nothing marks prose as
possibly out of date, and nothing tells the person the data has changed since the view was
written. **Target (proposed, Q4):** each snapshot widget shows when it was written (the revision
that last set it), and `V` shows "Data changed since this view was written · N changes" when
revisions after `V.updatedRev` touched entities its queries read. Until that exists, the
acceptance check is that `V` uses `Text` values instead of numbers typed into prose: a Callout
that states a count is a view-quality failure.

## 5 Allowed view shape

- `V` must be a **retained** view: `kind` cleared by Keep (`apps/web/src/pages/answers.ts:4`) or created as an
  ordinary view. An unkept answer expires after 7 days (`apps/server/src/views/service.ts:23`) and
  drops out of the tabs. It still renders by direct URL (`ProjectPage.tsx:274`), but that is not
  the reuse path this case accepts.
- At least one **action surface** for `T`: TaskTable, TaskChecklist or KanbanBoard (in-widget
  checkbox), or any query-bound list whose rows open the drawer (`DataTable`/`DataList` rows,
  `generic.tsx:98`). The gallery's "What's overdue?" answer uses DataTable
  (`guidance.ts:57`–`:100`), so the drawer path must work.
- Every widget that lists or counts tasks is bound by query/filter. Copying task titles or counts
  into Callout/Markdown/StatCards `value` is not allowed for facts that can change (CLAUDE.md
  "Views"; `guidance.ts:40`).
- Status in queries is written by meaning (`done`, `cancelled`) or by `P`'s values, never by a
  built-in name the project doesn't use as a value or meaning.
- Prose is allowed for interpretation (why something matters), at most one Callout and one
  Markdown block in this case's view, so the snapshot rows in section 4 stay checkable.
- Any layout; widget IDs must stay stable between the action and reuse.

## 6 Failure & fallback behavior

### Validation rules

| Rule | Today (code) | Target |
| --- | --- | --- |
| Entity belongs to the project of the view | **Not enforced on update.** `/api/apply` takes no project context (`app.ts:175`). An update addresses only `type` + `id` (`store.ts:535`), so a request could change a task in `Q` while the person is on `P`'s page. `data.projectId` may also be changed, and that is accepted if the task's references stay in one project (`store.ts:800`). The UI only sends ids from its own dataset, which limits this to stale or crafted requests. | View actions carry the project id; the server rejects an update whose entity is not in that project, and rejects `projectId` changes from view actions (400, entity named). |
| Option value valid **for that project** | Enforced on every write: `status` must be one of `P`'s values (`store.ts:821`). Error: `…: status "done" isn't one of this project's task status options (queued, building, review, waiting, accepted, dropped)`. UI controls build values from `P`'s options (`interactive.tsx:217`, `drawer.tsx:150`). | Unchanged, plus: when `P` has **no** option with the requested meaning, `valueFor` silently falls back to the first option (`options.ts:198`), so "Mark done" would write `queued`. Target: the action is refused with "This project has no status that counts as done", and no revision is written. |
| Choose by meaning, never by built-in name | Done for checkbox/Start (`valueFor`), and display uses `meaningOf` (`interactive.tsx:234`). Tests: `apps/web/src/catalog/options.test.tsx:59`. | Same; the checks in section 3 step 3 fail if `done` is sent for `P`. |
| Date format | `dueDate` must be `YYYY-MM-DD` (`z.iso.date()`, `entities.ts:33`, `:108`); a bad value fails with `data.dueDate: …` (400). The date input sends ISO dates or `null` to clear (`editable.tsx:231`). | Same; one revision per committed date (variant C-2). |
| Required fields | Strict schema on the merged entity (`store.ts:658`): `title` non-empty, `status`/`priority` required (a `null` status in an update deletes the key and then fails parsing), unknown fields rejected. `message` required and trimmed non-empty (`packages/schema/src/revisions.ts:58`). | Same. |
| References | `assigneeId` must name an existing assignee (any project, since assignees are workspace-wide); `stageId` must be a stage of the same project (`store.ts:780`–`:801`). | Same. |

### Outcomes by failure type

| Case | Today (from code) | Target |
| --- | --- | --- |
| **Duplicate submission** (double-click, or a second click before the result lands) | The checkbox has no pending/disabled state. Two clicks before the reload send the same `accepted` twice: the second update changes nothing, and the transaction rolls back with `revision: null` (`store.ts:477`, `:717`), so one revision is recorded. A click **after** the reload lands toggles: it sends `queued` (`interactive.tsx:244`) and records a second revision "Mark … as queued", reopening the task. No network-level retry exists (`api.ts:32`). | Exactly one revision per intended action. The control shows pending and ignores clicks until the result and reload land; a repeated "mark done" never reopens. The toast appears once. |
| **Stale revision** (an agent set `T` to `waiting` after the page loaded, before the owner clicks) | No precondition: the request carries no expected value or base revision, so it is last-write-wins per field (`store.ts:535`–`:541`). In the same process the SSE reload usually arrives first. From the stdio agent there is up to a ~1 s polling gap (`feed.ts:17`), during which the click overwrites `waiting` with `accepted` silently. The overwrite is visible only afterwards, as `before.status: "waiting"` in `R1`. Undo of an action whose field changed later is refused with `409 … status was changed later` and shown as "Couldn’t save: …" (`store.ts:587`, `ProjectPage.tsx:460`). | The action sends the value it saw (`expect: {status: "queued"}`) or `T.updatedRev` (already on every entity, `entities.ts:341`). If it no longer matches, the server returns 409 naming the current value and its author, writes nothing, and the UI reloads and says "This task changed to Waiting (by Planning agent). Mark done anyway?" A confirmed retry is a new revision. |
| **Invalid value** | Server 400 with the issue text above. The UI shows "Couldn’t save: Invalid changes" plus the issues and reloads, so the view keeps the stored state (no optimistic update to roll back, `ProjectPage.tsx:203`–`:211`). The missing-meaning fallback is the exception: it writes a wrong but valid value. | 400 as today, with a plain-language message that names the field and the allowed labels (not raw values); the missing-meaning case is refused (above). |
| **Server failure** | 500 → "Couldn’t save: Internal error" (`app.ts:66`–`:79`). Network down → `"Couldn’t save: TypeError: Failed to fetch"` (raw `String(err)`). The transaction rolls back, so there is no partial revision (`store.ts:485`). The reload fails but the last data stays on screen (`api.ts:76`–`:85`). If the response is lost **after** commit, the reload shows the change as applied, and a retry is a no-op. After an SSE reconnect, missed revisions are not reloaded: the server sends `ready` with `latest` (`app.ts:110`), but the client ignores it (`events.ts:34`–`:41`) until the next revision or focus. | Plain message ("Pharos couldn’t save — the task is unchanged") with Retry that re-sends the same intent (safe because it is idempotent and carries the precondition). On SSE reconnect, reload when `latest` exceeds the last revision seen. The server stays up (CLAUDE.md background-callback rule). |
| **Undo** | No toast for checkbox, Start, drag or drawer dropdowns (W1.1, `interactive.tsx:219`, `drawer.tsx:94`); revert from History works and conflicts surface (`apps/web/src/catalog/history.test.tsx:92`, `apps/server/src/store/store.test.ts:339`). | Status actions from views are undoable as in step 6 (Q2). |

## 7 Completion condition

Case C is complete when one recorded run on the built fixture shows all of the following, with
the browser evidence (screenshots or recording) and the revision JSON (`GET /api/revisions/R1`)
attached:

1. The action produced exactly one revision whose author, message, and single before/after change
   match section 3 step 4, with `accepted` (not `done`) stored.
2. L1–L9 held in both windows within 2 s, without reload or refocus; L10 and Undo (step 6)
   restored every widget, with `R2.revertOf = R1`.
3. Each section 6 row has a passing check: duplicate (one revision, no reopen), stale (409 and
   nothing written), invalid (400, view unchanged), server failure (unchanged task, recoverable),
   cross-project update refused.
4. After R4/R5, reopening `V` without asking again showed the live rows of section 4 updated (`T`
   gone, `U` present, `${late}` correct), snapshot prose unchanged, and `V.updatedRev` unchanged.
5. An agent's `changes_since(P)` reported `R1` (and `R2`/`R3`) with the human author and message.
   This ties the run to goal_06edae668e9a.

Rows marked Target in section 6 are expected to **fail today**. Recording those failures, rather
than passing them, is the expected outcome of a baseline run.

## 9 Open questions for the owner

- **Q1 (W8):** Confirm status → done-meaning as the measured action, with owner and due date as
  variants, or pick one of those instead.
- **Q2:** Should every status action from a view (checkbox, Start, drag, dropdown) offer the Undo
  toast, or only the checkbox? Today none of them does.
- **Q3:** For stale writes, should the server refuse (409 plus confirm) or apply with a visible
  "overwrote Waiting set by …" notice? The target above assumes refuse.
- **Q4:** Is a "data changed since this view was written" hint plus per-prose timestamps the right
  reuse signal? Or should the agent be asked to refresh prose, which would cost a run?
- **Q5:** Should kept views be offered when asking a similar question (C-7)?
- **Q6:** What should "Mark done" do in a project with no status that counts as done: refuse
  (target) or offer to add one?
- **Q7:** Is 2 s the right live-update bound, given that agent writes from another process arrive by
  1 s polling?
