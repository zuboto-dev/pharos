## 2 Rules common to every target

### 2.1 Notation and summary statistics

- `b` is a value from the frozen W3 baseline, and `i` is the same value from the W15 run of the
  improved workflow. "X(i) ≤ 1.25·X(b)" means the W15 value must not exceed 1.25 times the W3 value.
- Every target uses only the valid **gating runs** of that case and phase (§2.2).
- **Pooled rate:** Σ numerators / Σ denominators over all gating runs. For facts that is Σf / ΣN over
  the checkpoints W1.5 §3 defines, with "first output" scored before corrections and "final" after
  them. Completion is ΣC / number of runs (or repetitions, for B and C).
- **Mean per run:** used for correction burden and its parts. W1.5 writes burden as `B = H + A`.
  Here it is spelled out as burden = owner corrections `H` + agent repairs, so the letters are not
  confused with cases A and B.
- **med** is the upper median, the value at rank ⌊n/2⌋+1 in ascending order (the middle value when n
  is odd). **p90** is the value at rank ⌈0.9·n⌉.
- **Ranking of missing values:** in TTUC, `not_reached` ranks as +∞. In total latency, a run with
  `C = 0` (including deadline) ranks as +∞, because a failed run is not a delivery time. Cost, tokens
  and tool calls use every valid run, failed or not, because the spend is real either way.
- **Product time (PT)** is an interval minus the union of owner-activity intervals inside it: scripted
  waits and think time, the reuse delay, owner typing, and the A §7 reader exercise. Absolute time
  ceilings apply to PT. Relative time clauses use the raw W1.5 values. See amendment M1.
- **Contemporaneous cost** is W1.5's primary `cost_usd` when the provider reports it. Otherwise it is
  `estimated_cost_usd` on the rate card current at the run. **Constant-rate cost** is W1.5's reprice of
  both phases on the reference rate card frozen at W3.
- **Tokens** means `I + W + O` (uncached input, cache-write input, output), in W1.5's disjoint
  categories. Cache reads `R` are reported but not budgeted, so prompt caching is not penalized.
- **Undefined baseline:** if `b` is `not possible`, `not_reached`, or a +∞ median, the relative clause
  is dropped and only the absolute clause applies. A `null` or `capture_error` baseline is not
  undefined. W3 must be completed before W15.

## 5 Zero-tolerance list

**Silent data loss** means a persisted value is removed or overwritten, or a write fails, and the
actor who loses it is not shown an explicit conflict, error or notice. **A stale or unintended
mutation** is a write committed on the basis of state that changed after the actor saw it, a second
write from one intended action, or a write the case script did not ask for.

**Rule.** One violation in any W15 execution on the release-candidate commit makes the G5 result FAIL,
whatever the other metrics say. That includes gating runs, probes, diagnostic variants, replacement
runs, and runs declared capture-invalid whose revision and change export is intact. A check that is
not observed in every planned W15 execution is not met, because missing evidence is not a pass. W3
outcomes are recorded. Several items are expected to fail there, and that gates nothing.

## 6 Statistical handling

### 6.1 Run counts and what they can detect

- **A, 46 runs per phase.** If 5% of runs have a side effect (ZT-1), at least one shows up with
  probability 91%. Zero in 46 bounds the rate below 6.3% (95% one-sided). The standard error of pooled
  completion near 80% is about 0.06. For facts, about 800 facts per phase give a standard error of
  about 0.015 for the difference between phases, and more once correlation within a run is counted.
  The core phrasings carry most facts, so they get 5 runs. The variants get 3, which bounds the owner's
  reading work at 46 reader exercises per phase.
- **B, 5 repetitions plus 10 `B-agent` runs.** Deterministic steps must pass 5 of 5. That catches a 20%
  intermittent failure with probability 67% and a 50% race with probability 97%. The agent step is
  observed 15 times per phase. If 10% of agent edits overwrite owner work, ZT-2 sees it at least once
  with probability 79%. Zero in 15 bounds the rate below 18%.
- **C, 5 repetitions.** All deterministic, with the same detection as B's deterministic steps.

These sizes detect regressions of roughly 15 to 20 percentage points in A's pooled rates. Smaller
differences are within noise, and the fixed rules in §3 decide. The margins (0.02 for facts, 0.05 for
completion, one run per variant) are there so an unchanged product isn't failed by noise alone.

### 6.2 Variance and intermittent failures

- Each run is scored on its own. An intermittent failure is a failure of the run it occurs in. There
  is no best-of, no majority vote, and no retrying until a run passes.
- Agent variation is absorbed by pooled rates with stated margins in A and by k-of-n rules for B's
  agent step. Deterministic behavior has no allowance: n of n.
- Every individual value is published, along with medians and p90 with their n and per-variant
  tables (W1.5 §8 item 5).

### 6.3 Invalid runs and replacements

- A run can be replaced only if W1.5 classifies it `capture_error`, or if it is `environment_invalid`
  with independent evidence. That evidence is a provider HTTP 5xx or 429, or a documented outage in the
  raw transcript, a host failure unrelated to Pharos, or a harness defect fixed without a product
  change. Timeouts, runner errors, crashes and wrong answers without such evidence are valid failed
  runs.
- A replacement uses the next repetition index under the same session conditions. Each planned run
  gets at most 2 replacements. If more than 20% of a case-phase's planned executions are invalid, the
  case-phase is void: fix the harness, rerun the whole case-phase, and publish every attempt.
- Zero-tolerance evidence from an invalid run still counts (§5).

### 6.4 Matched conditions, drift and re-baselining

- W15 uses the agent configuration frozen at W3: the resolved model id for each request, the agent
  CLI version, reasoning and sampling settings, and enabled tools. It also uses the same machine class,
  the same OS and browser major versions, and the same schedule.
- If any of these must change, the baseline commit is re-run at W15 with the new configuration for
  every gating agent run. Examples are a retired model or a different default agent shipped by the
  product. These baseline runs alternate with the improved runs, one repetition each. For facts and
  completion, `b` is then the higher of the two baselines, so a configuration change cannot lower the
  correctness bar. For burden, time, tool calls, tokens and cost, `b` is the re-run baseline, because
  those depend on conditions.
- **Drift check.** Even when nothing changed, W15 starts by running the baseline commit on A1, A3 and
  `B-agent`, 5 runs each. Compare each subset with the same subset in W3. The result is treated as
  drift if any of these hold:
  - the median TTUC, latency, constant-rate cost or tool calls differs by more than 25%
  - pooled F_init differs by more than 0.10
  - completion differs by 2 or more runs

  On drift, re-baseline as above. The drift-check runs are published either way.

### 6.5 What counts as met

- A target is met only if every clause holds at full measured precision. Nothing is rounded before
  comparison, and "close" is not met.
- Every gating run must be valid and have the metric complete. A W15 value that is `null` or
  incomplete means not met.
- Correction burden counts only if W1.5 §4's reviewer agreement passes in both phases. Unresolved
  burden is not met.
- A case is met when all its targets are met. The release verdict is **PASS** when all of these hold:
  - zero zero-tolerance violations
  - cases A, B and C met
  - every run carries the W1.5 §5 version set

  Otherwise it is **FAIL**, and the report lists each unmet clause with its numbers. The owner makes
  the release call, but a FAIL cannot be reported as "targets met".

### 6.6 Freezing and rebinding

- These targets are fixed when the owner accepts the decision in W1.8. After the first W3 run they can
  change only through §6.4, or through a superseding owner decision recorded, with its reason, before
  the first W15 run. Such a decision reruns W3 if it changes checks (W1.5 §0).
- Reconciling the cases with the fixtures (§1) is allowed only before the first W3 run, and only as a
  published mapping from old to new check ids and expected sets. Formulas, floors, budgets and ZT ids
  stay unchanged. A ZT or completion check may be dropped only if the behavior it tests no longer
  exists in the case, and only with the owner's acceptance.
- Some case questions are answered later: W1.4 Q1 in W8, plus W1.3 Q1, Q4 and W1.4 Q2, Q3, Q6. If an
  answer changes a case after W3, that case's W3 baseline is rerun under the new version, and the
  formulas here carry over unchanged.
- All W15 executions run on one release-candidate commit, with a clean tree and the full SHA recorded.
  The planned set runs once per commit. Re-running the same commit for a better sample is not allowed.
  A new attempt needs a new commit with a documented product change and reruns every gating set. G5
  publishes every attempt.

## 8 Why these numbers

- **Correctness is kept, not traded.** PLAN asks to preserve correctness, so facts have no improvement
  requirement. They have a floor plus a margin of about one standard error. The A floors (0.90 for the
  first output, 0.95 after at most one correction) are levels where the owner can rely on an answer
  without checking it. B and C test deterministic state and rendering, so anything below all facts
  correct is a bug. B's 0.98 leaves room only for the agent step.
- **Completion is the improvement goal.** G2 and G3 exist to make these workflows completable. A must
  halve its failure rate, with at least 4 of 5 answers fully usable. The requirement is capped at 90%
  so a near-perfect baseline is not asked for the impossible, and a 0.05 margin still blocks a real
  regression. B and C have no baseline completion by construction, so their targets are absolute.
- **Correction burden.** Owner corrections must at least halve, to at most one run in four. That
  ceiling means first answers are usually right. Total burden, which counts agent repairs, must fall
  by 30%. The weaker requirement is deliberate: semantic validation can surface more agent self-repairs,
  and those already cost time and money in the latency and cost targets.
- **Time to useful content.** A historical answer for a small project took 11 s of agent time after the
  agent was briefed up front. With the 2 s batching wait and rendering, a 45 s median ceiling allows
  about three times that for validation and previews, and the 1.25× relative clause will usually bind
  first. The p90 ceiling of 120 s caps the tail. B's TTUC is product time for a few saves and reloads,
  so 10 s is generous for an immediate UI. C uses the cases' own 2 s live-update bound, which already
  allows for the 1 s polling of other processes, in every repetition. Its median is 1.0 s because the
  owner's own write is announced in-process at once.
- **Total latency is a budget, not a goal.** A may be at most 25% slower than the baseline, with PT
  ceilings of 90 s for A (one answer, settling, and room for one correction), 120 s for B (one targeted
  agent edit plus the owner's saves and reloads) and 20 s for C (no model).
- **Cost.** The historical figures are not a benchmark. M4 answers cost USD 1.0–1.7. After briefing the
  agent up front, a small project answer cost USD 0.45 (3 tool calls) and a Pharos-sized one USD 0.81
  (4 turns). A's median budget of USD 1.00 sits above the briefed range and below the pre-briefing
  range. The per-run cap of USD 2.00 is above the old USD 1.7 high, so only runaway runs or runs with a
  correction hit it. B's agent edit is a smaller task than an answer, so its budget is USD 0.60
  median and USD 1.20 per run. C needs no model. The 1.25× constant-rate clause separates product
  changes from price changes. These are budgets for the matched agent configuration, not price claims.
- **Tool calls and tokens are efficiency budgets.** The 1.5× multiplier, or +3 and +2 calls, reflects
  how lumpy small counts are: going from 3 calls to 5 is +67% and trivial. The per-run caps of 25 and 12
  catch loops. Tokens exclude cache reads, so the budget measures new input and output, not cheap
  re-reads.
