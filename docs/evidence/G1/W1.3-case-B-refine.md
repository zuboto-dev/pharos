## 1 Purpose & goal link

**Goal:** "People can refine and act through generated views with control" (`goal_c111358c4d9b`).
Case B covers the _refinement → retention_ part of the roadmap's question → view → action →
refinement → reuse workflow (`docs/PLAN.md:14`) and feeds the G3 exit evidence "saved-view round
trip, … Undo, preserved layout" (`docs/PLAN.md:21`).

**What the case proves when it passes:** the owner can change what a generated table shows (filter
and columns) and how a chart groups (grouping), each change is saved as an attributed, undoable
revision, the result survives a full browser reload, and a later agent edit to the same view keeps
every widget id, every owner-set prop and the owner's ordering intact, with history that can tell
human work from agent work.

**Why it matters:** if refinement is impossible or an agent's later edit silently overwrites it, people
stop refining and fall back to asking for a new view each time, which defeats retention and reuse.

## 5 Allowed view shape

The agent is an LLM, so A2 may differ from the reference call. The case passes if the board after
the agent's round trip satisfies all of the following:

- **Ids:** `summary`, `chart`, `tasks` retained with the same component; exactly one new widget, a
  `Stat` (or `StatCards` with one stat) counting current-stage tasks with blocked meaning (value or
  meaning name accepted). Its id is free but must not reuse an existing id.
- **Owner-set props untouched:** everything listed in check 2. The agent may set `chart.sort` and may
  change `summary` (width or text) only as needed to place the new widget.
- **Placement:** the new widget sits in the first row next to `summary`; `chart` stays before `tasks`.
- **Layout:** every width ≥ its component's `minColumns`; `view_preview` reports no layout warnings
  (no partial rows), which rules out leaving the Stat alone on a 3-column row.
- **Method:** `ops` preferred. A full `widgets` replacement is acceptable only if the result
  satisfies every rule above; record the method used. `resetToTemplate` is not allowed (the view has
  no template, so it is rejected anyway, `service.ts:237`).
- **Revisions:** target one agent revision; at most two (a self-correction after reading the preview)
  still passes, and each extra revision is recorded as correction burden. Creating a new view or an
  answer view instead of editing this one fails the main path.
- **No copied data:** the new widget reads data through a query; it must not hard-code a count
  (`Stat.value`-style fixed numbers or literal numbers in Text content fail).

## 7 Completion condition

Case B is **complete (pass)** for a run when, observed in the browser and in
`history_list(entityId=<viewId>)` / `view_get(viewId)` after R2:

1. Steps S0–R2 were all performed through the intended surfaces (UI for the owner, MCP for the agent).
2. The board equals the A2 row of §4 (or satisfies §5 for a non-reference agent call), and every check
   in §4 holds.
3. The view has 7 revisions (5 human, 2 agent) — up to 8 with one agent self-correction.
4. Undo probes U1–U7 behave as specified.
5. Failure probes F1, F2, F2b and F4 produce the target behavior; F3 is recorded as **pending W6**
   until W6 lands, after which it becomes required.

**Today's expected baseline result: not completable in the UI.** H1, H2 and the grouping part of H3
must be recorded as **"not possible"**; S0, S1, S2, H4, S3, R1, A1, A2, R2 and U1, U5, U6a, U6b, U7
can be run. F2 fails (accepted with a warning only on MCP); F1 is partial; F3 is pending W6 and is
silent today. The B-sim variant (§8) can measure the agent-preservation half today.

Record per run: model and client of the agent, its reasoning setting, prompt text, the A2 call(s)
verbatim, the preview it received, revision list with authors and messages, wall-clock from the owner's
instruction to V7, agent usage/cost as reported by the client (no price quoted), and screenshots after
H4, R1 and R2.
